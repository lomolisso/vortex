# 0.1 — Fixes to atomics, LR/SC and cache ordering

Base: upstream Vortex `b8c5a2433` (2026-09-30). Branch `dlmem`.

This version fixes bugs in upstream Vortex that the project's features (DLMEM,
mbarriers, DXA × DLMEM) build on. Every bug was in the original upstream code.
The part names (A1, A6, …) come from the project plan; the parts are listed in
the order they were made, because later parts refer to earlier ones.

## Terms

- **Warp, lane:** a warp is a group of threads that run the same instructions
  together. A unit with N lanes handles N threads at a time.
- **Core, socket, cluster:** a socket is a group of cores that share L1 caches;
  a cluster is a group of sockets that can share an L2 cache. An L3 cache, if
  present, serves all clusters.
- **Local memory:** a small fast memory in each core (CUDA's "shared memory"),
  split into banks. A bank serves one access per cycle.
- **DMA port:** a second local-memory port that reads or writes a whole row
  (one word in every bank) at once. The DXA copy engine writes through it; the
  tensor unit reads through it.
- **Atomic (AMO):** an instruction such as `amoadd` that reads a word, changes
  it and writes it back as one step that nobody can interrupt.
- **LR/SC:** `lr` reads a word and *reserves* it. `sc` writes the word only if
  no one else wrote it since; otherwise it fails and the program retries. A
  reservation belongs to one hardware thread (hart), named by a **hart id**
  `{core, warp, thread}`.
- **Last-level cache (LLC):** the last cache before main memory (L3, else L2,
  else L1). Atomics on main memory run there.
- **Write-through cache:** a cache that passes every store on to the next
  level at once, instead of keeping it.
- **RTL / SimX:** the hardware description and its C++ model. Both must behave
  the same.

## A1 — an atomic was lost when a DMA access hit its bank

**Problem.** A local-memory atomic uses its bank for 3 cycles. A DMA access
could take the bank in the middle. Then the atomic's result was lost or
written to the wrong word, or the atomic wrote over the data the DMA had just
written.

**Change** (`hw/rtl/mem/VX_local_mem.sv`). A DMA access waits while any bank it
uses has an atomic in progress (at most 2 cycles), and meanwhile no new atomic
can start there. With atomics or DMA disabled, the hardware is the same as
before.

## A6 — `sc` succeeded after a DXA copy overwrote the reserved word

**Problem.** RISC-V requires an `sc` to fail when another device wrote the
reserved word. In the RTL, DMA writes never cancelled reservations. In SimX,
they cancelled only reservations on the first word of the written block, and
on core 0 never the one of thread 0.

**Change.**
- RTL (`VX_local_mem.sv`): a DMA write now cancels every reservation on the
  words it writes, the same way a normal store does. This adds no cycles.
- SimX (`sim/simx/types.h`, `dxa/dxa_core.cpp`, `amo/amo_unit.h`,
  `mem/local_mem.cpp`): DXA writes carry a new `dma` flag, and local memory
  cancels every reservation on any word such a write touches.

## A7 — threads of one warp shared one hart id

**Problem.** When the load/store unit (LSU) has fewer lanes than a warp has
threads, it sends the warp in parts. For example, with 2 lanes and 4 threads,
lane 0 carries thread 0 in the first part and thread 2 in the second. The RTL
built the hart id from the lane number, so threads 0 and 2 got the same id.
Thread 2 could then `sc` on thread 0's reservation, and an update was lost.

**Change** (`hw/rtl/core/VX_lsu_slice.sv`). The thread field is the real
thread number: part × lanes + lane, as `mhartid` already uses. The default
configuration (one part) is unchanged.

## A10 — LR/SC loops could starve

**Problem.** While a thread holds a reservation, other threads' `lr` on that
word are refused, up to a fixed number: 7 in local memory, 63 in the LLC. After
that, the next `lr` takes the reservation. With many threads, the refusals ran
out before the holder's `sc` arrived, so the `sc` failed, again and again: in
local memory with more than 16 threads per core, and in the LLC with 256
threads in the GPU. For example, with 8 threads per warp, the other 7 threads
of the holder's own warp used up all 7 refusals.

**Change.** The refusal counter gets more bits when more threads can compete,
so each of them can be refused at least once:
- local memory (`VX_local_mem.sv`): `max(3, log2(warps × threads))` bits; in
  the default configuration (4 warps × 4 threads), 7 → 15 refusals;
- LLC (`hw/rtl/cache/VX_cache_amo.sv`): `max(6, log2(threads in the whole
  GPU))` bits; the default stays at 63.

`hw/rtl/cache/VX_amo_unit.sv`: comments only.

## A11 — with 32+ warps, one group of warps could keep another out of local memory

**Problem.** A core with 32 or more warps has 2 or more LSU blocks (copies of
the load/store unit). Their lanes reach the local-memory banks through a
crossbar, a switch that picks one lane when several want the same bank. The
RTL crossbar always let block 0 win (fixed priority). So if warps of block 0
keep reading a flag that a warp of block 1 must set, block 1 never gets the
bank and the program hangs. SimX crossbars always used fixed priority for
requests, whatever policy they were given, so SimX's caches and main memory
also differed from their RTL, which takes turns (round-robin). SimX also
served the DMA ports last, where the RTL serves them first.

**Change.**
- RTL (`VX_local_mem.sv`): the bank crossbar takes turns (round-robin).
- SimX (`types.h`, `core.h`, `core.cpp`, `socket.cpp`, `mem/local_mem.h`,
  `mem/local_mem.cpp`, `mem/cache.cpp`, `mem/memory.cpp`):
  - each crossbar now follows its policy;
  - round-robin works like the RTL's, for requests and responses: it starts
    at port 0, and the turn moves on only when a request is accepted;
  - local memory serves DXA, then the tensor unit, before the LSU lanes;
  - caches and main memory use round-robin, as their RTL does.

**Effect.** Some programs take a slightly different number of cycles; for
example, on the RTL the sgemmx matrix multiply takes 3.8% fewer. As a chip
design (ASIC), A10 and A11 together make the core about 0.8% larger; its
maximum clock speed does not change.

## A8 — cores of different clusters shared one hart id

**Problem.** The core field of the hart id had only enough bits for the cores
of one cluster, but it held the core's number in the whole GPU, so the top bits
were lost. With 2 clusters of 2 cores, core 2 got the same id as core 0. The
L3 serves both clusters, so there core 2 could `sc` on core 0's reservation.

**Change.**
- `hw/rtl/VX_gpu_pkg.sv`: a new `NUM_TOTAL_CORES` counts the cores really
  built (clusters × sockets × cores per socket), and the core field is sized
  from it. With one cluster the hardware is unchanged, unless a socket is
  larger than `NUM_CORES`: such a socket builds extra cores, and they now get
  their own ids too.
- `VX_lsu_slice.sv`: a check stops the simulation if a core number does not
  fit.
- `VX_cache_amo.sv`: A10's LLC counter uses the same count.

## A9 — atomics were wrong with more than one last-level cache, or none

**Problem.** Atomics are correct only if they all run in one LLC. Some
configurations have more than one LLC, or none:
- 2 or more clusters with an L2 but no L3 (each L2 is an LLC);
- no L2 or L3, and more than one L1 data cache (for example `--cores=2`, where
  each core has its own L1);
- no L1 data cache, no L2 and no L3.

There, atomics gave wrong results without any error.

**Change.** When atomics are enabled (the RISC-V "A" extension; off by default,
but the Vulkan tests turn it on), these configurations are rejected with the
error "the A extension needs one shared last-level cache: enable L2 (one
cluster) or L3 (several clusters)".
- SimX (`sim/simx/processor.cpp`): the build stops with this error.
- RTL (`hw/rtl/Vortex.sv`): the RTL simulators (rtlsim, xrtsim) stop with this
  error at start. Like Vortex's other configuration checks, it does not run
  when the RTL is turned into a chip (synthesis).

## A12 — the cache could lose or reorder accesses to the same word

**Problem.** Accesses to the same word must take effect in the order they
arrive; for one thread, that is program order. When a cache does not have a
line yet, requests for it wait until it arrives, and must still keep that
order. The upstream cache broke the order, or lost data, in these cases:

| # | What went wrong | Needs atomics? |
|---|---|---|
| 1 | an atomic arriving right after another overwrote the first one's result | yes |
| 2 | an atomic's delayed write landed after a newer store: the store was lost | yes |
| 3 | an atomic or `lr` overtook an older store of the same thread | yes |
| 4 | a load overtook an older atomic and read the old value | yes |
| 5 | in write-through caches, a load overtook an older store and read the old value | no |
| 6 | a store that had to wait wrote its data early: an older load saw the newer value | no |
| 7 | the queue of finished atomic results could overflow, losing results | yes |
| 8 | when the cache was briefly blocked, a load right after an atomic could read the value from before it | yes |

In SimX, a store after an atomic could be lost in memory when the LLC is
write-through.

**Change.**
- Atomic unit (`hw/rtl/cache/VX_cache_amo.sv`):
  - an atomic or `sc` waits one cycle while the previous atomic is still being
    computed (bug 1);
  - a delayed atomic write never overwrites a newer store (bug 2);
  - each bank accepts only as many atomics as its result queue holds, at most
    4 (bug 7);
  - a load right after an atomic gets the new value even before it is written
    into the cache, also while the cache is blocked (bug 8).
- Ordering check, which makes an access wait for older accesses to the same
  word (`hw/rtl/cache/VX_cache_bank.sv`, `VX_cache_mshr.sv`):
  - atomics count as writes, and atomics wait like loads and stores do
    (bugs 3, 4);
  - the check also works in write-through caches (bug 5);
  - a store that must wait does not touch the data until its turn (bug 6).
- SimX (`sim/simx/mem/cache.cpp`): at a write-through LLC, a store waits behind
  any older atomic to the same cache line.

**Effect.** Programs that do not hit these cases take the same number of
cycles. As a chip design (ASIC), the cache is 0.08% larger and reaches a 5.8%
higher maximum clock speed.

## Environment

- Dev container (`miscs/docker/dev-entrypoint.sh`, `docs/environment_setup.md`):
  the container set the environment variable `XLEN`, and `config.mk` keeps an
  `XLEN` that is already set, so 64-bit build directories were silently built
  as 32-bit. The container now uses the name `CONFIG_XLEN`.
- Dev image build (`miscs/docker/vortex-dev.sh`, `Dockerfile.dev`,
  `README.md`): only the `ci/` scripts are copied into the image, not the test
  cases or baselines, so editing tests no longer makes Docker reinstall the
  toolchain. A comment notes that tests must not run in parallel inside one
  build directory.
- `ci/install_dependencies.sh`: a new `--synth` option (also run by `--all`)
  installs Tcl, which the prebuilt Yosys and OpenSTA need to start.

**Left for a human:** regenerate the CI baselines these changes moved:
performance `core:sgemmx-nt4`, `dxa:perf_gate-sgemm2-dxa-nt16`,
`dxa:perf_gate-wgmma-dxa` (A11), and the cache's synthesis baseline (A12).

New tests and CI cases come with each fix; they are not described here.
